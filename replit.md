# Quality Voice Operations (QVO) — Multi-Tenant SaaS

## Overview
QVO is a multi-tenant SaaS platform for managing AI-powered voice operations at an enterprise scale. It provides solutions for deploying and managing AI agents, handling customer interactions, and delivering advanced analytics. The platform aims to revolutionize customer service and sales by enabling businesses to efficiently leverage AI for voice interactions. Key capabilities include a visual agent builder, a real-time voice gateway, robust analytics, AI workforce orchestration, cost optimization, advanced observability, and a marketplace for agent templates. It features three distinct control planes: a **Tenant Portal**, a **Platform Admin Console**, and an **Operations Console**, with access managed via a 4-tier RBAC system. The business vision is to revolutionize how enterprises manage their voice channels, driving efficiency, improving customer satisfaction, and unlocking new revenue opportunities through AI.

## User Preferences
- Logging: Color-coded, session-scoped, PHI redacted
- Safety: Medical guardrails strictly enforced (never bypassed)
- Fail-closed: All auth/crypto/webhook secrets required in production

## System Architecture
The QVO platform comprises three main components: a React-based admin dashboard (`client-app`), an Admin REST API (`server/admin-api`), and a Voice Gateway (`server/voice-gateway`).

### UI/UX
The `client-app` is built with React 19, Vite 6, Tailwind CSS 4, TypeScript, and Zustand. It is wired up with **i18next + react-i18next** so the dashboard, marketing site, admin console, and docs can be served in multiple languages — English ships as the default, Spanish ships as a proof-of-concept second locale, and a visible language switcher in every shell persists the choice to `localStorage["qvo_lang"]`. Locale files live under `client-app/src/locales/<lang>/`; see `docs/i18n.md` for how to add a new language. It features a responsive design with public marketing pages and a protected dashboard. The **Tenant Portal** sidebar is condensed to 10 business-focused tabs. The **Platform Admin Console** (purple) and **Operations Console** (emerald) maintain independent navigation. A core UI element is the **Agent Builder (Agent Studio)**, a visual drag-and-drop workflow builder utilizing `@xyflow/react`, including a node library, configuration panels, and deployment management with version control. A **Platform Assistant** provides in-app, context-aware guidance via OpenAI function calling. The UI adheres to QVO brand guidelines using Deep Harbor (#123047), Signal Teal (#2E8C83), Clinic Mist (#F3F7F7) colors and Sora, Manrope, Inter fonts.

### Technical Implementation
- **Admin API (`server/admin-api/`):** An Express 5 application providing JWT-authenticated, RBAC-enabled access to platform resources. It manages tenant configurations, agent workflows, Stripe billing, usage metering, campaign management, knowledge base operations, and analytics, enforcing trial guardrails, rate limiting, and auto-suspension policies.
- **Voice Gateway (`server/voice-gateway/`):** Functions as a Twilio webhook and OpenAI Realtime WebSocket bridge. It manages the call lifecycle, routes calls based on database configurations, and handles audio streaming for the embedded website widget, including a SIP audio fix for codec compatibility.
- **Database:** PostgreSQL with Row-Level Security (RLS) enforced for tenant-scoped operations. Migrations are managed via numbered SQL files.
- **Core Services (`platform/`):** A suite of core services including Audit, Billing & Usage, Analytics, Campaigns, Integrations, RBAC, Tenant Management, Agent Templates & Marketplace, Telephony & Messaging, Runtime, Email, Tools, Knowledge Management, Reasoning Framework, Workflow engine, Mini Systems (SMS Inbox, Scheduling, Enterprise Ticketing, Dispatch), Advanced Observability, AI Workforce Operating System, AI Business Autopilot, Global Intelligence Network (GIN), Simulation Lab, and Website Agent & Widget.
- **Enterprise Ticketing System:** Full-lifecycle ticket management with features like categories, activity timeline, internal notes, watchers, SLA policies, macros, template responses, saved views, custom fields, workflow rules, linked tickets, bulk actions, and reporting dashboard.
- **Enterprise Scheduler:** A comprehensive scheduling system including providers, provider schedules, schedule overrides, appointment types, resources, booking rules, waitlist, reminder configurations, recurring appointments, and a full scheduling audit log. It offers various calendar views and reporting dashboards.
- **Connector Hub (`platform/integrations/connectors/`):** A plug-and-play integration system with adapters for HubSpot, Google Calendar, Outlook Calendar, Slack, Zapier, Twilio SMS, and ticketing. It dispatches standard events to active connectors and includes SSRF protection for any customer-supplied URL via `ssrfGuard.ts`: the helper resolves the hostname via DNS, blocks any IPv4/IPv6 address in private/loopback/link-local/cloud-metadata ranges, and pins outbound connections to the validated IP (with the original `Host:` header and TLS SNI) to defeat DNS-rebinding attacks. It is used by the Zapier webhook and external Ticketing adapters. A `ConnectorAuthAlertScheduler` runs every 30 minutes, scans for connectors in auth-error / `needs_reconnect` state, and emails the workspace's admins (with a deep link to `/connectors?provider=…` so the link still resolves to the right connector card whether the integration row is in `needs_reconnect` state or has been removed entirely; the `SyncErrorAlerter`'s per-event/sustained/recovery email + SMS + in-app surfaces use the same provider-keyed link form). The `auth_alert_sent_at` column on `integrations` dedupes alerts until the connector recovers and fails again. **Per-tenant alert preferences** (`connector_alert_settings` + `connector_alert_mutes`, managed in *Settings → Notifications*) let owners/managers (a) silence alerts for an entire provider or a single integration row — honoured by both the auth-alert scheduler and `SyncErrorAlerter` (failure email/in-app, sustained-failure SMS, and recovery alerts) — and (b) opt into a daily-digest mode that batches every currently-failing connector into a single tenant-wide email at most once per 24 hours instead of one email per incident. In-app notifications still fire individually under the existing 24h `tenant_notifications` throttle. A tenant can have both Google and Outlook calendar connectors enabled simultaneously; each agent and phone number carries an optional `scheduling_provider` column and `ConnectorService.dispatchEvent` filters scheduling targets to the chosen provider (phone-number choice wins over agent choice; null on both falls back to broadcasting to every enabled scheduling integration).
- **Security:** Incorporates PHI redaction, encryption of tenant secrets, and strict enforcement of JWT, Stripe, and connector encryption keys.
- **Frontend/Backend Communication:** Utilizes an API proxy for routing and Server-Sent Events (SSE) for real-time data updates.
- **Federated Ingest API:** Supports federated agent ingestion via REST API, enabling external voice agent systems to push call completion and ticket creation events into QVO. Endpoints are authenticated via API key, rate-limited, and use atomic idempotency. Federated agents are read-only in the platform.
- **Native Agent Porting (Azul Vision):** Supports running Azul Vision's production agents natively inside QVO's WebSocket-based voice gateway. This involves specific integrations for ticketing and schedule lookups, dual-write mechanisms for tickets, and custom prompts for ophthalmology-specific content.

## Operations
- **Production runbook:** `docs/deployment-checklist.md` is the source of truth for required env vars, webhook setup (Twilio, Stripe, Cal.com), seeding, and the security checklist. Update it whenever a new env var, webhook, or deployment-time step is added.
- **Book-a-Demo / Cal.com webhook:** the public `/book-demo` page embeds a Cal.com (or Calendly) scheduler controlled by `VITE_BOOK_DEMO_SCHEDULER_URL` (+ optional `VITE_BOOK_DEMO_SCHEDULER_PROVIDER`). The Admin API exposes `POST /book-demo/calendar-webhook`, which verifies an HMAC-SHA256 signature using `CALCOM_WEBHOOK_SECRET` and fails closed in production. Booking lifecycle and lead-capture alerts go out via the **Sales Inbox alert pipeline** (`server/admin-api/services/marketing-leads.ts`): channels (email/Slack), recipients, per-event toggles and an optional Slack webhook are stored in `platform_settings.sales_alert_settings` (migration `072_sales_alert_settings.sql`) and editable at runtime under **Admin → Sales Inbox → Alert settings** (`GET`/`PUT /platform/sales-alert-settings`). When unset, the pipeline falls back to the env defaults (`SALES_NOTIFICATION_EMAIL` for email, `OPS_SLACK_WEBHOOK_URL` for Slack). Each `marketing_leads` row is alerted at most once — `marketing_leads.notified` is flipped to `true` only after a successful send, and alert messages embed a deep link of the form `<PLATFORM_ADMIN_BASE_URL>/admin/sales-inbox#lead-<id>` that auto-expands the row on arrival. Cal.com webhook must subscribe to `BOOKING_CREATED`, `BOOKING_RESCHEDULED`, and `BOOKING_CANCELLED` and point at `https://<admin-host>/book-demo/calendar-webhook` — full setup steps in `docs/deployment-checklist.md` §5.
- **Sales Inbox CSV export:** `GET /platform/marketing-leads.csv` (platform-admin only) streams the current Sales Inbox view as CSV using the same `source` / `booking` / `status` / `q` filters as the listing endpoint. The route is backed by `iterateLeadsForExport` in `server/admin-api/services/marketing-leads.ts`, which paginates through `marketing_leads` in batches of 500 to avoid loading the full result set into memory. The Sales Inbox page (`AdminSalesInbox.tsx`) exposes a "Download CSV" button that fetches the file with the admin Bearer token and triggers a Blob download.
- **Hard-bounce reason backfill:** `scripts/backfill-retry-skipped-reason.ts` is a one-off (re-runnable) ops script that fills the `retry_skipped_reason` column added by `migrations/072_retry_skipped_reason.sql` for historical rows that failed before every write path stamped the column. It walks `support_ticket_replies` (outbound only), `support_tickets`, and `docs_feedback_replies`, runs the server-side `isPermanentSmtpError` classifier (`platform/email/smtpErrorClass.ts`) against `email_error`, and stamps `retry_skipped_reason = 'permanent_smtp_failure'` on rows that classify as a hard bounce. Skips rows that already have a non-NULL value, so re-runs are no-ops. Supports `--dry-run` for ops to preview impact before writing. Run once per environment after `migrations/072_retry_skipped_reason.sql` is applied: `APP_ENV=production PLATFORM_DB_POOL_URL=... npx tsx scripts/backfill-retry-skipped-reason.ts`. After the backfill, the `isHardBounce` legacy client-side classifier branch in `client-app/src/lib/smtpErrorClass.ts` becomes pure belt-and-suspenders for any future schema gaps.

## External Dependencies
- **Database:** PostgreSQL (Supabase for production).
- **Payment Processing:** Stripe (checkout, webhooks, customer portal, metered billing).
- **Telephony:** Twilio (voice calls, SMS messaging, webhooks, number provisioning).
- **AI/ML:** OpenAI (Realtime API, `text-embedding-3-small`, various GPT models).
- **Email:** Nodemailer (SMTP service).
- **CAPTCHA:** Cloudflare Turnstile (for signup verification).
- **Frontend Libraries:** Zustand, `@tanstack/react-query`, `@xyflow/react`.
- **Inbound Email:** SendGrid Inbound Parse (for support ticket replies).
