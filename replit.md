# Quality Voice Operations (QVO) — Multi-Tenant SaaS

## Overview
QVO is a multi-tenant SaaS platform for managing AI-powered voice operations at an enterprise scale. It provides solutions for deploying and managing AI agents, handling customer interactions, and delivering advanced analytics. The platform aims to revolutionize customer service and sales by enabling businesses to efficiently leverage AI for voice interactions. Key capabilities include a visual agent builder, a real-time voice gateway, robust analytics, AI workforce orchestration, cost optimization, advanced observability, and a marketplace for agent templates. It features three distinct control planes: a **Tenant Portal**, a **Platform Admin Console**, and an **Operations Console**, with access managed via a 4-tier RBAC system. The business vision is to revolutionize how enterprises manage their voice channels, driving efficiency, improving customer satisfaction, and unlocking new revenue opportunities through AI.

## User Preferences
- Logging: Color-coded, session-scoped, PHI redacted
- Safety: Medical guardrails strictly enforced (never bypassed)
- Fail-closed: All auth/crypto/webhook secrets required in production

## System Architecture
The QVO platform comprises three main components: a React-based admin dashboard (`client-app`), an Admin REST API (`server/admin-api`), and a Voice Gateway (`server/voice-gateway`).

### UI/UX
The `client-app` is built with React 19, Vite 6, Tailwind CSS 4, TypeScript, and Zustand. It is wired up with **i18next + react-i18next** for multi-language support (English default, Spanish PoC). It features a responsive design with public marketing pages and a protected dashboard. The public top nav exposes Product and Solutions as dropdowns surfacing the developer marketing pages (Federated Ingest, Global Intelligence Network) and the vertical agents catalog; the `/resources` search box also searches the marketing-pages index in `client-app/src/data/marketingPages.ts`. The **Tenant Portal** sidebar is condensed to 10 business-focused tabs. The **Platform Admin Console** (purple) and **Operations Console** (emerald) maintain independent navigation. A core UI element is the **Agent Builder (Agent Studio)**, a visual drag-and-drop workflow builder utilizing `@xyflow/react`, including a node library, configuration panels, and deployment management with version control. The voice picker in the Agent Builder's right-side config panel is a custom radio-style list (recommended voices first, then "other voices") with a per-row preview button that streams a short OpenAI TTS sample of the agent's welcome greeting in the selected language. Previews are served by `POST /agents/voice-preview` (admin API), use the `gpt-4o-mini-tts` model, and are cached server-side per `(voice, language, greeting hash)` with a 24h TTL and per-user rate limit (30 req/min) to avoid re-synthesis on every click. A **Platform Assistant** provides in-app, context-aware guidance via OpenAI function calling.
- **Design System — Refined Harbor (locked 2026-04-27):** The QVO visual language is defined as a single source of truth across two paired files: `client-app/src/index.css` (`@theme` block — runtime CSS vars) and `client-app/src/lib/designTokens.ts` (typed mirror for charts/canvas/programmatic access). Brand pigments are Deep Harbor `#0E2738`, Signal Teal-evolved `#1F8E83` primary, warm amber `#E2A24A` accent, paired with Sora display + Inter body. Tokens cover palette (light + dark), radii (6/10/14/20/pill), spacing (4px grid), elevations (`--elevation-1/2/3/glow`, harbor-tinted soft shadows), motion (120/200/320ms × `cubic-bezier(.2,.8,.2,1)`), and an a11y floor (`--focus-ring-*`, `--touch-target-min`). A global `:focus-visible` outline rule applies the focus ring everywhere automatically. The 3-direction comparison that informed the lock-in is preserved at `/internal/design-directions` (page: `client-app/src/pages/DesignDirections.tsx`, mockup canvas: `artifacts/mockup-sandbox/src/components/mockups/QvoDesignDirections.tsx`). All polish rules, migration steps, and the per-component "what Refined Harbor looks like" guide live in `docs/design-system.md` — read it before restyling any page.

### Technical Implementation
- **Admin API (`server/admin-api/`):** An Express 5 application providing JWT-authenticated, RBAC-enabled access to platform resources. It manages tenant configurations, agent workflows, Stripe billing, usage metering, campaign management, knowledge base operations, and analytics, enforcing trial guardrails, rate limiting, and auto-suspension policies.
- **Voice Gateway (`server/voice-gateway/`):** Functions as a Twilio webhook and OpenAI Realtime WebSocket bridge. It manages the call lifecycle, routes calls based on database configurations, and handles audio streaming for the embedded website widget, including a SIP audio fix for codec compatibility.
- **Federal DNC Registry Sync (`platform/campaigns/FederalDncService.ts` + `FederalDncSyncScheduler.ts`):** Weekly platform-scoped pull of the FTC National Do-Not-Call Registry into `federal_dnc_numbers` (PK `phone_number`, with `registry_version`) plus a singleton `federal_dnc_sync_state` row tracking the last sync (started/completed/version/count/status). Started from `server/admin-api/start.ts` (10-minute boot delay, 7-day interval, graceful stop on SIGTERM). The campaign pre-flight in `ComplianceService.ts` now batch-decrypts each contact page and consults both the per-tenant `dnc_list` *and* `federal_dnc_numbers`; matches are tagged `source: 'tenant' | 'federal'` (tenant wins on overlap so subtotals always sum to `dncMatchCount`), and the launch-blocked path in `routes/campaigns.ts` surfaces the subtotals + registry version in the error message and audit `afterState`. The scheduler/dialer's runtime DNC re-check (`isContactOnDnc`) returns `{ onDnc, source, registryVersion }` and emits a dedicated `campaign.federal_dnc_block` audit event (with `actorUserId: 'system'` + `registryVersion`) whenever a federal-only block fires. The Campaigns UI (`client-app/src/pages/Campaigns.tsx`) renders "Tenant DNC" vs "Federal DNC" badges per match and shows the registry version in the compliance panel.
- **Trusted Caller Service (`platform/telephony/TrustedCallerService.ts`):** Tenant-scoped registry of verified outbound caller IDs (Twilio OutgoingCallerIds + Trust Hub product/brand SIDs) used by outbound campaigns. Supports register/verify/sync/rotate/delete and exposes `resolveCampaignCallerId` so the `CampaignScheduler` can dial from a brand-attested number that carriers attest A under STIR/SHAKEN. Surfaced under the tenant Configure nav as Trusted Callers and selectable per campaign in the create modal. Health: `checkCallerHealth` queries Twilio's OutgoingCallerIds + Trust Hub TrustProducts + BrandRegistrations endpoints to compute one of `healthy | expiring_soon | expired | revoked | unknown` (`EXPIRING_SOON_THRESHOLD_DAYS=14`). The weekly **`VerifiedCallerHealthScheduler`** sweeps `verified_caller_ids`, persists the result, demotes attestation on revoked rows, and dispatches in-app + email alerts (one per caller per week) using the same `fanoutInAppNotification` + `getTenantAlertEmailRecipients` pipeline as the connector auth alerter. The **`VerifiedCallerSyncScheduler`** polls every 3 minutes for rows still in `pending` (across all tenants via `withPrivilegedClient`), calls `syncCallerIdStatus` per caller (which is tenant-scoped + RLS-respecting), promotes verified rows automatically, marks rows past `VERIFICATION_TTL_MS` as `failed`, and fires a one-shot `trusted_caller_verified` in-app notification on the `pending → verified` transition (preferring the registering user, falling back to tenant alert recipients). The Trusted Callers page renders a per-row "expires in N days" badge driven by the recorded health columns.
- **Database:** PostgreSQL with Row-Level Security (RLS) enforced for tenant-scoped operations. Migrations are managed via numbered SQL files. **Analytics-table indexing strategy:** every high-volume per-tenant table that drives a customer-facing dashboard carries a composite `(tenant_id, <time-column> DESC, <kind>)` index so the planner can serve range-and-filter queries without sequential-scanning. Migration `078` established the pattern for `usage_metrics(tenant_id, period_start DESC, metric_type)` and `call_events(tenant_id, occurred_at DESC)`; migration `081` extends it to `call_sessions(created_at, lifecycle_state)`, `tool_invocations(invoked_at, status)`, `workflow_executions(started_at, status)`, `audit_logs(occurred_at, action)`, `analytics_metrics(recorded_at, metric_name)`, and `call_events(occurred_at, event_type)`. New per-tenant time-series tables added in future migrations should follow this same triple.
- **Core Services (`platform/`):** A suite of core services including Audit, Billing & Usage, Analytics, Campaigns, Integrations, RBAC, Tenant Management, Agent Templates & Marketplace, Telephony & Messaging, Runtime, Email, Tools, Knowledge Management, Reasoning Framework, Workflow engine, Mini Systems (SMS Inbox, Scheduling, Enterprise Ticketing, Dispatch), Advanced Observability, AI Workforce Operating System, AI Business Autopilot, Global Intelligence Network (GIN), Simulation Lab, and Website Agent & Widget.
- **Enterprise Ticketing System:** Full-lifecycle ticket management with features like categories, activity timeline, internal notes, watchers, SLA policies, macros, template responses, saved views, custom fields, workflow rules, linked tickets, bulk actions, and reporting dashboard.
- **Enterprise Scheduler:** A comprehensive scheduling system including providers, provider schedules, schedule overrides, appointment types, resources, booking rules, waitlist, reminder configurations, recurring appointments, and a full scheduling audit log. It offers various calendar views and reporting dashboards.
- **Connector Hub (`platform/integrations/connectors/`):** A plug-and-play integration system with adapters for HubSpot, Google Calendar, Outlook Calendar, Slack, Zapier, Twilio SMS, and ticketing. It dispatches standard events to active connectors and includes SSRF protection for customer-supplied URLs. It supports per-tenant alert preferences for connector authentication issues and sync errors.
- **Security:** Incorporates PHI redaction, encryption of tenant secrets, and strict enforcement of JWT, Stripe, and connector encryption keys.
- **Linting (`eslint.config.mjs` + `tools/eslint-rules/`):** Minimal ESLint v9 setup that runs only over `client-app/src/**` and `platform/**`. The single enabled rule is the local `local/no-cents-divided-by-100`, which guards against the recurring off-by-100x bug by flagging inline `(...Cents) / 100` math outside the canonical `formatCurrency.ts` helpers (BL-023). Justified exceptions (HTML number-input bindings) use `// eslint-disable-next-line local/no-cents-divided-by-100`. Run with `npm run lint`; rule self-tests via `npm run lint:rules`.
- **Frontend/Backend Communication:** Utilizes an API proxy for routing and Server-Sent Events (SSE) for real-time data updates.
- **Federated Ingest API:** Supports federated agent ingestion via REST API, enabling external voice agent systems to push call completion and ticket creation events into QVO. Endpoints are authenticated via API key, rate-limited, and use atomic idempotency. The live `/v1/ingest/calls` endpoint accepts events whose `start_time` is within the last 7 days; older events (up to 30 days) must be sent through `/v1/ingest/calls/backfill` with an explicit `backfill_attestation` block (BL-041). Idempotency is keyed on `(tenant_id, idempotency_key)` only, so the same `external_id` can be re-issued with a fresh token to correct historical records.
- **Native Agent Porting (Azul Vision):** Supports running Azul Vision's production agents natively inside QVO's WebSocket-based voice gateway, including integrations for ticketing and schedule lookups.
- **Technician Mobile App (`mobile/`):** A standalone Expo (React Native) app for field technicians built on `expo-router` + `@tanstack/react-query` + `expo-secure-store`. It authenticates with a tenant API key (prefix `vai_`) against `/api/v1/dispatch/*` and `/api/v1/scheduling/*` (mounted in `server/admin-api/routes/mobileApi.ts`) so a technician can view assigned jobs, accept/decline, drive the dispatch state machine (`assigned → en_route → on_site → in_progress → completed`), see upcoming appointments, check in / complete bookings, and one-tap call/SMS/email the customer. The job detail screen renders an inline `react-native-maps` preview (`components/JobMapPreview.tsx`) with the destination pin, the technician's current location, and a haversine-based ETA estimate; tapping the address or the Directions button opens Apple/Google Maps for turn-by-turn navigation (helpers in `lib/maps.ts`). Location uses `expo-location` (foreground permission) and is gracefully skipped if access is denied. The same screen exposes a **Complete with photos & notes** sheet (`mobile/components/CompletionSheet.tsx`) that uses `expo-image-picker`/`expo-camera` to capture or pick photos, asks the server for a presigned URL via `POST /api/v1/dispatch/uploads/request-url`, PUTs the binary directly to Replit Object Storage, then registers the file via `POST /api/v1/dispatch/jobs/:id/attachments` (which writes to `dispatch_job_attachments`, sets a private tenant-scoped ACL, emits an `attachment_added` row in `dispatch_job_events`, and optionally atomically transitions the job via `completion_transition`). Uploaded photos and notes are surfaced inline both in the mobile job detail (timeline + photo strip) and in the admin dispatch board's attachments + activity tabs (`/dispatch/attachments/:id/file` streams files through tenant-scoped JWT/cookie auth). Builds for iOS + Android via EAS profiles defined in `mobile/eas.json` (bundle id / package `com.voiceai.tech`). When a job moves to `en_route`, `on_site`, or `in_progress` the app starts a foreground+background GPS subscription (`mobile/lib/locationTracking.ts`) and posts each fix to `POST /api/v1/dispatch/resources/:id/location`; tracking automatically stops on `completed` / `incomplete` / `cancelled` / `done`. The tracker is owned by an app-level component (`mobile/components/LocationTrackingGate.tsx` mounted under `AuthGate`), so navigating away from the job-detail screen does not interrupt tracking. Permission strings in `mobile/app.json` make clear the device is only tracked while a job is active. To prevent intra-tenant location spoofing (the mobile API key is tenant-wide), the location endpoint requires an `X-Device-Secret` header; that secret is issued only by `POST /api/v1/mobile/devices/enroll`, which consumes a one-time pairing code that an admin generates via `POST /dispatch/resources/:id/pairing-codes` and surfaces in the **Pair device** action on the admin Resources tab. The technician enters the code once under **Profile → Live location** (`mobile/app/(tabs)/profile.tsx`) and the device is bound to that specific resource; the secret is decoupled from push registration so location works even when push permission is denied. The dispatcher Live Map tab in `client-app/src/pages/Dispatch.tsx` polls `GET /dispatch/resource-locations` every 15 s and renders Leaflet markers (loaded on demand from CDN — no npm dep added) color-coded by job status, with a popup that links back to the job detail. Migrations `083_dispatch_resource_locations.sql` (latest-fix + history tables, tenant RLS, history pruned to 200 rows per resource), `084_user_devices_secret.sql` (per-device secret hash), and `085_dispatch_resource_pairing_codes.sql` (admin-issued single-use codes) back this flow.

## External Dependencies

- **Payment Processing:** Stripe (checkout, webhooks, customer portal, metered billing).
- **Telephony:** Twilio (voice calls, SMS messaging, webhooks, number provisioning).

- **Email:** Nodemailer (SMTP service).
- **CAPTCHA:** Cloudflare Turnstile (for signup verification).
- **Frontend Libraries:** Zustand, `@tanstack/react-query`, `@xyflow/react`.
- **Inbound Email:** SendGrid Inbound Parse (for support ticket replies).
- **Scheduling:** Cal.com (or Calendly) via webhooks for demo bookings.
