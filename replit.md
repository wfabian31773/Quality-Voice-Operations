# Quality Voice Operations (QVO) — Multi-Tenant SaaS

## Overview
QVO is a multi-tenant SaaS platform designed to manage AI-powered voice operations for enterprises. It enables the deployment and management of AI agents, handles customer interactions, and provides advanced analytics to revolutionize customer service and sales. Key capabilities include a visual agent builder, a real-time voice gateway, robust analytics, AI workforce orchestration, cost optimization, advanced observability, and an agent template marketplace. The platform features a **Tenant Portal**, **Platform Admin Console**, and **Operations Console**, secured by a 4-tier RBAC system. The vision is to enhance efficiency, improve customer satisfaction, and create new revenue opportunities through AI in voice channels.

## User Preferences
- Logging: Color-coded, session-scoped, PHI redacted
- Safety: Medical guardrails strictly enforced (never bypassed)
- Fail-closed: All auth/crypto/webhook secrets required in production

## System Architecture
The QVO platform consists of a React-based admin dashboard (`client-app`), an Admin REST API (`server/admin-api`), and a Voice Gateway (`server/voice-gateway`).

### UI/UX
The `client-app` is built with React 19, Vite 6, Tailwind CSS 4, TypeScript, and Zustand, supporting multiple languages via `i18next`. It features a responsive design and a protected dashboard. Key UI elements include the **Agent Builder (Agent Studio)** for visual workflow creation using `@xyflow/react`, with version control and a voice picker. A **Platform Assistant** provides context-aware guidance through OpenAI function calling. The **Design System — Refined Harbor** defines the visual language using a unified approach for runtime CSS variables and typed design tokens, ensuring consistent branding.

### Technical Implementation
- **Admin API (`server/admin-api/`):** An Express 5 application offering JWT-authenticated, RBAC-enabled access to tenant configurations, agent workflows, billing, usage metering, campaign management, knowledge base operations, and analytics. It enforces trial guardrails, rate limiting, and auto-suspension policies.
- **Voice Gateway (`server/voice-gateway/`):** Acts as a Twilio webhook and OpenAI Realtime WebSocket bridge, managing call lifecycles, routing, and audio streaming for the embedded website widget.
- **Federal DNC Registry Sync:** Implements weekly synchronization with the FTC National Do-Not-Call Registry to block calls.
- **Trusted Caller Service:** Manages tenant-scoped verified outbound caller IDs (Twilio OutgoingCallerIds + Trust Hub) for STIR/SHAKEN attestation.
- **Database:** PostgreSQL with Row-Level Security (RLS) for multi-tenancy. Analytics tables are indexed for efficient querying.
- **Core Services (`platform/`):** A comprehensive suite covering Audit, Billing & Usage, Analytics, Campaigns, Integrations, RBAC, Tenant Management, Agent Templates & Marketplace, Telephony & Messaging, Runtime, Email, Tools, Knowledge Management, Reasoning Framework, Workflow engine, Mini Systems (SMS Inbox, Scheduling, Enterprise Ticketing, Dispatch), Advanced Observability, AI Workforce Operating System, AI Business Autopilot, Global Intelligence Network (GIN), Simulation Lab, and Website Agent & Widget.
- **Marketplace Usage Reporting:** Marketplace add-on subscriptions report consumption to Stripe via the Billing Meter Events API.
- **Enterprise Ticketing System:** Provides full-lifecycle ticket management.
- **Enterprise Scheduler:** A comprehensive system for managing appointments, schedules, and resources.
- **Connector Hub (`platform/integrations/connectors/`):** A plug-and-play integration system with adapters for various third-party services, featuring SSRF protection and alert preferences.
- **Security:** Incorporates PHI redaction, encryption of tenant secrets, and strict enforcement of JWT, Stripe, and connector encryption keys.
- **Inbound webhook replay protection:** All inbound webhooks are layered behind a replay-resistant defense (audit + remediation tracked in #942). **Twilio voice/SMS** (`/twilio/voice`, `/twilio/status`, `/twilio/outbound`, `/twilio/sms`, `/twilio/sms-status`): Twilio's `X-Twilio-Signature` is HMAC-SHA1 over (URL + sorted form params) with NO embedded timestamp, so a captured payload would otherwise verify forever. After the signature passes, `server/voice-gateway/middleware/twilioSignature.ts` derives a per-route nonce (`MessageSid` for inbound SMS, `MessageSid + MessageStatus` for SMS-status callbacks so the queued→sent→delivered chain isn't blocked, `CallSid + SequenceNumber` for voice-status callbacks, `CallSid` for voice/outbound) and consults the two-layer cache in `server/voice-gateway/middleware/twilioReplayCache.ts`: an in-memory LRU+TTL fast path plus a durable Postgres backend (table `twilio_webhook_replay_nonces`, migration `migrations/100_twilio_webhook_replay_nonces.sql`) that uses a single `INSERT ... ON CONFLICT (nonce) DO UPDATE ... WHERE expires_at <= NOW() RETURNING (xmax = 0)` claim — atomic across concurrent gateway instances, TTL-aware so expired nonces are reclaimed (a captured payload re-fired after the window is allowed exactly once, matching Cal.com / Stripe semantics), with a probabilistic out-of-band `DELETE` keeping the table self-pruned. Default window 300s, 10k in-memory entries; tunable via `TWILIO_REPLAY_WINDOW_SECONDS` / `TWILIO_REPLAY_CACHE_MAX_ENTRIES`. A second hit on the same nonce returns 403 and increments the new `replay_detected` reason in `twilioSignatureMetrics.ts` (alert threshold = 1/min, surfaced via `getTwilioSignatureMetrics`). The durable layer fails open on a Postgres outage (in-memory still enforces) so a DB blip doesn't take voice down. **Cal.com & Calendly** (`/book-demo/calendar-webhook`, `/book-demo/calendly-webhook`): already timestamp-bound HMAC (sender-supplied `t=` is signed and validated against a 5-minute window — see `tests/marketing/calcomBookingWebhook.test.ts` for the canonical replay-protection test pattern that the Twilio tests in `tests/security/twilioSignatureMiddleware.test.ts` mirror). **Stripe** (`/billing/stripe-webhook`): `stripe.webhooks.constructEvent` enforces the SDK-default 300s tolerance on the signed `t` element of `Stripe-Signature`, so no extra layer is required (commented inline in `server/admin-api/routes/billing.ts`). **SendGrid Inbound Parse** (`/support/inbound`): static `SUPPORT_INBOUND_SECRET` only — the provider does not sign payloads. Documented inline in `server/admin-api/routes/support.ts` with mitigations (HTTPS-only transport, idempotent ticket-side processing) and a follow-up to either move to a signed flow or add a content-hash + timestamp nonce cache modeled on the Twilio one.
- **Linting:** Uses ESLint v9 with a custom rule (`local/no-cents-divided-by-100`) to prevent common currency calculation errors.
- **Type-checking gate:** Every pull request runs the `client-app tsc --noEmit` job defined in `.github/workflows/typecheck.yml`, which fails the PR build if any new TypeScript errors are introduced. This catches unsafe casts, missing modules, and broken globals that the production Vite build does not flag. Mark this job as a required status check in branch protection so PRs cannot merge while it is failing. The same check also runs locally as a safety net via `scripts/post-merge.sh`. The underlying script is `npm run typecheck:client` from the repo root (or `npm run typecheck` from `client-app/`), both of which invoke `tsc --noEmit` against `client-app/tsconfig.json`.
- **Sales Inbox e2e gate:** Every pull request also runs the `Sales Inbox filters e2e` job defined in `.github/workflows/sales-inbox-e2e.yml`. The job spins up a disposable PostgreSQL 16 service container, runs all SQL migrations, seeds the platform admin user, boots the Platform Dev stack (vite on :5000 + admin API on :3002 via `scripts/start-platform-dev.sh`), waits for both ports to become healthy, installs the Playwright Chromium browser, and runs `npm run test:e2e:sales-inbox-filters` against `tests/e2e/salesInboxFilters.spec.ts`. This catches regressions in the `actedOnBy`/`inactiveDays` filter inputs, the autocomplete `<datalist>`, the negative-value rejection on the numeric input, and the "Download CSV" URL — all of which the SQL-only unit tests in `tests/admin-api/marketingLeadsFilters.test.ts` cannot exercise. On failure, Platform Dev's stdout/stderr is uploaded as a `platform-dev-logs` artifact for debugging.
- **OpenAI Realtime voice drift detector:** A daily GitHub Action (`.github/workflows/check-openai-realtime-voices.yml`, 13:17 UTC + manual trigger) runs `scripts/check-openai-realtime-voices.ts`, which probes `POST https://api.openai.com/v1/realtime/sessions` with a deliberately invalid voice and parses the allowed-value list out of the resulting `error.message` (multiple wording patterns are supported — see `parseAllowedVoicesFromErrorMessage`). It diffs the discovered set against `VOICES` in `client-app/src/lib/agentVoices.ts` and on drift opens (or updates the body of) a single deduplicated tracking issue labeled `openai-voices-check`, with a per-run comment for re-detections. When a subsequent run comes back in-sync, the workflow auto-closes any open tracking issue (with a comment linking to the verifying run) so the team doesn't have to remember to clean up. Exit codes are split: 0=in-sync, 1=drift, 2=parser-broken (OpenAI changed wording), 3=request/auth failure — and HTTP 401/403/429/5xx from OpenAI are explicitly classified as `request_failed` (not `parser_broken`) so transient upstream issues blame OpenAI rather than this script. Requires the `OPENAI_API_KEY` secret on the Actions runner (the probe is expected to 400, costs nothing). Unit tests live in `tests/scripts/checkOpenaiRealtimeVoices.test.ts`. Complements the existing review-cadence comment block in `agentVoices.ts` / `agentLanguages.ts` and the CI guard from task #709 (which catches *removals* but not *additions*).
- **i18n key sync gate:** `npm run check:i18n-keys` (via `scripts/check-i18n-keys.mjs`) walks every namespace shipped from `client-app/src/locales/{en,de,es,fr,pt-BR}/*.json` and asserts that every key in `en/<ns>.json` is present in every other locale file (and vice versa). The list of supported locales and namespaces is parsed out of `client-app/src/lib/i18n.ts` so adding a new locale or namespace doesn't require updating the script. Drift fails CI (exit 1) and prints the missing/extra dotted key paths per locale/namespace. Intentional language-specific overrides are tolerated via `scripts/i18n-allowed-overrides.json` (`missing` / `extra` buckets per locale per namespace; today both are empty). The same logic is also covered by `tests/scripts/i18nKeyCheck.test.ts` so it runs under `vitest`. Wired into the existing PR `Typecheck` workflow (`.github/workflows/typecheck.yml`, runs right after `client-app tsc --noEmit`) so pull requests fail fast on translation drift, AND into `scripts/post-merge.sh` between the typecheck and design-system checks for local parity. Catches the silent "user sees `vertical_agents_page.spotlight.partner_cta` instead of a translated string" regression.
- **Localized URL routing:** Visitors can land on `/<locale>/...` (e.g. `/pt-BR/pricing`, `/fr/docs`) or use `/?lang=<locale>` as a shareable, search-engine-indexable language signal. The URL prefix wins over `localStorage`/`navigator.language`, every page emits per-locale `<link rel="alternate" hreflang>` tags via the `SEO` component, and the language picker rewrites the URL on switch. Un-prefixed URLs continue to work; `/en/...` is accepted as an alias of `/...`. See `docs/i18n.md` for details.

## External Dependencies
- **Database:** PostgreSQL (Supabase for production).

- **Telephony:** Twilio (voice calls, SMS messaging, webhooks, number provisioning).
- **AI/ML:** OpenAI (Realtime API, `text-embedding-3-small`, various GPT models).
- **Email:** Nodemailer (SMTP service), SendGrid Inbound Parse (for support ticket replies).
- **CAPTCHA:** Cloudflare Turnstile.
- **Frontend Libraries:** Zustand, `@tanstack/react-query`, `@xyflow/react`.
- **Scheduling:** Cal.com (or Calendly) via webhooks.
