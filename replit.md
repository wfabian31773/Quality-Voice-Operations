# Quality Voice Operations (QVO) — Multi-Tenant SaaS

## Overview
QVO is a multi-tenant SaaS platform designed to manage AI-powered voice operations for enterprises, enhancing customer service and sales. It facilitates the deployment and management of AI agents, handles customer interactions, and provides advanced analytics. Key features include a visual agent builder, a real-time voice gateway, robust analytics, AI workforce orchestration, and an agent template marketplace. The platform offers a Tenant Portal, Platform Admin Console, and Operations Console, secured by a 4-tier RBAC system, aiming to boost efficiency, improve customer satisfaction, and create new revenue streams through AI in voice channels.

## User Preferences
- Logging: Color-coded, session-scoped, PHI redacted
- Safety: Medical guardrails strictly enforced (never bypassed)
- Fail-closed: All auth/crypto/webhook secrets required in production

## System Architecture
The QVO platform consists of a React-based admin dashboard (`client-app`), an Admin REST API (`server/admin-api`), and a Voice Gateway (`server/voice-gateway`).

### UI/UX
The `client-app` is built with React 19, Vite 6, Tailwind CSS 4, TypeScript, and Zustand, supporting multiple languages via `i18next`. It features a responsive design and a protected dashboard. The **Agent Builder (Agent Studio)** uses `@xyflow/react` for visual workflow creation with version control and an OpenAI TTS-powered voice picker. UI elements within the Agent Builder are localized based on the user's interface language, while agent-produced strings remain in the agent's spoken language. A **Platform Assistant** provides context-aware guidance using OpenAI function calling. The **Design System — Refined Harbor** ensures visual consistency using runtime CSS variables and typed design tokens.

### Technical Implementation
- **Admin API (`server/admin-api/`):** An Express 5 application offering JWT-authenticated, RBAC-enabled access to tenant configurations, agent workflows, billing, usage metering, campaign management, knowledge base operations, and analytics. It enforces trial guardrails, rate limiting, and auto-suspension policies.
- **Voice Gateway (`server/voice-gateway/`):** Acts as a Twilio webhook and OpenAI Realtime WebSocket bridge, managing call lifecycles, routing, and audio streaming for the embedded website widget. It includes replay protection for inbound webhooks.
- **Federal DNC Registry Sync:** Implements weekly synchronization with the FTC National Do-Not-Call Registry to block calls, with platform admins able to force syncs.
- **Trusted Caller Service:** Manages tenant-scoped verified outbound caller IDs (Twilio OutgoingCallerIds + Trust Hub) for STIR/SHAKEN attestation.
- **Database:** PostgreSQL with Row-Level Security (RLS) for multi-tenancy. Analytics tables are indexed for efficient querying.
- **Core Services (`platform/`):** A comprehensive suite covering Audit, Billing & Usage, Analytics, Campaigns, Integrations, RBAC, Tenant Management, Agent Templates & Marketplace, Telephony & Messaging, Runtime, Email, Tools, Knowledge Management, Reasoning Framework, Workflow engine, Mini Systems (SMS Inbox, Scheduling, Enterprise Ticketing, Dispatch), Advanced Observability, AI Workforce Operating System, AI Business Autopilot, Global Intelligence Network (GIN), Simulation Lab, and Website Agent & Widget.
- **Marketplace Usage Reporting:** Marketplace add-on subscriptions report consumption to Stripe via the Billing Meter Events API, ensuring idempotency.
- **Enterprise Ticketing System:** Provides full-lifecycle ticket management including categories, timelines, notes, SLA policies, reporting, and custom fields.
- **Enterprise Scheduler:** A comprehensive system for managing appointments, schedules, providers, resource booking rules, waitlists, and reminders.
- **Connector Hub (`platform/integrations/connectors/`):** A plug-and-play integration system with adapters for various third-party services (HubSpot, Google Calendar, Outlook Calendar, Slack, Zapier, Twilio SMS, ticketing), featuring SSRF protection and alert preferences. The CRM caller-identity revalidation sweep emits in-process counters (`CrmCallerIdentityRevalidationMetrics`) — scanned/validated/staleScrubbed/skippedNoConfig/failed totals plus per-tenant breakdown and recent-cycle history — surfaced on the Platform Admin Connector Health view so ops can spot stale-scrub volume and per-tenant failure spikes without grepping logs.
- **Security:** Incorporates PHI redaction, encryption of tenant secrets, and strict enforcement of JWT, Stripe, and connector encryption keys.
- **Inbound webhook replay protection:** All inbound webhooks are layered behind a replay-resistant defense (audit + remediation tracked in #942). **Twilio voice/SMS** (`/twilio/voice`, `/twilio/status`, `/twilio/outbound`, `/twilio/sms`, `/twilio/sms-status`): Twilio's `X-Twilio-Signature` is HMAC-SHA1 over (URL + sorted form params) with NO embedded timestamp, so a captured payload would otherwise verify forever. After the signature passes, `server/voice-gateway/middleware/twilioSignature.ts` derives a per-route nonce (`MessageSid` for inbound SMS, `MessageSid + MessageStatus` for SMS-status callbacks so the queued→sent→delivered chain isn't blocked, `CallSid + SequenceNumber` for voice-status callbacks, `CallSid` for voice/outbound) and consults the two-layer cache in `server/voice-gateway/middleware/twilioReplayCache.ts`: an in-memory LRU+TTL fast path plus a durable Postgres backend (table `twilio_webhook_replay_nonces`, migration `migrations/100_twilio_webhook_replay_nonces.sql`) that uses a single `INSERT ... ON CONFLICT (nonce) DO UPDATE ... WHERE expires_at <= NOW() RETURNING (xmax = 0)` claim — atomic across concurrent gateway instances, TTL-aware so expired nonces are reclaimed (a captured payload re-fired after the window is allowed exactly once, matching Cal.com / Stripe semantics), with a probabilistic out-of-band `DELETE` keeping the table self-pruned. Default window 300s, 10k in-memory entries; tunable via `TWILIO_REPLAY_WINDOW_SECONDS` / `TWILIO_REPLAY_CACHE_MAX_ENTRIES`. - **Linting & Type-checking:** Uses ESLint v9 with custom rules (`local/no-cents-divided-by-100`, `local/no-dollars-times-100`, `local/no-literal-cta-name`) and a GitHub Action to enforce TypeScript type-checking. The two off-by-100x money rules run across the full workspace surface — `client-app/src/**`, `platform/**`, `mobile/**`, `widget/**`, `server/**`, and `shared/**` — so the same guard protects every part of the codebase that handles money. The shared canonical helpers live in three parallel locations so each layer can reach one without crossing layer boundaries: `client-app/src/lib/formatCurrency.ts` (web app), `platform/core/formatCurrency.ts` (platform/server), and `shared/billing/formatCurrency.ts` (the helper of last resort, importable from `mobile/`, `widget/`, `server/`, and the rest of `shared/`). All three expose the same `formatCurrency` / `formatCents` / `formatDollars` / `dollarsToCents` / `centsToWholeDollars` API and are the only files allowed to do raw `cents / 100` or `dollars * 100` math (whitelisted via the `ignores` list in `eslint.config.mjs`). The CTA literal rule stays scoped to `client-app/src/**` and `platform/**`. A GitHub Action also enforces TypeScript type-checking (`tsc --noEmit`) on every pull request. Every pull request runs the `client-app tsc --noEmit` job defined in `.github/workflows/typecheck.yml`, which fails the PR build if any new TypeScript errors are introduced. This catches unsafe casts, missing modules, and broken globals that the production Vite build does not flag. Mark this job as a required status check in branch protection so PRs cannot merge while it is failing. The same check also runs locally as a safety net via `scripts/post-merge.sh`. The underlying script is `npm run typecheck:client` from the repo root (or `npm run typecheck` from `client-app/`), both of which invoke `tsc --noEmit` against `client-app/tsconfig.json`.
- **Sales Inbox e2e gate:** Every pull request runs e2e tests for critical features like Sales Inbox filters using Playwright to catch UI regressions. The `Sales Inbox filters e2e` job defined in `.github/workflows/sales-inbox-e2e.yml` spins up a disposable PostgreSQL 16 service container, runs all SQL migrations, seeds the platform admin user, boots the Platform Dev stack (vite on :5000 + admin API on :3002 via `scripts/start-platform-dev.sh`), waits for both ports to become healthy, installs the Playwright Chromium browser, and runs `npm run test:e2e:sales-inbox-filters` against `tests/e2e/salesInboxFilters.spec.ts`. This catches regressions in the `actedOnBy`/`inactiveDays` filter inputs, the autocomplete `<datalist>`, the negative-value rejection on the numeric input, and the "Download CSV" URL. On failure, Platform Dev's stdout/stderr is uploaded as a `platform-dev-logs` artifact for debugging.
- **Status badge accessibility audit (`tenant-status-badge-axe`):** Authenticated tenant pages (Dashboard, Operations, Quality, Billing, Dispatch, SmsInbox) are scanned with axe-core in `tests/e2e/tenantStatusBadgeAxe.spec.ts` (npm script: `test:e2e:tenant-status-badge-axe`). The shared `StatusBadge` and `StatusDot` components emit `data-status-badge` / `data-status-dot` markers; the spec uses those selectors as the axe `include` context so the audit is scoped to the badge components and won't flag unrelated page-level a11y issues. The rule set is restricted to accessible-name and ARIA-plumbing rules (`role-img-alt`, `button-name`, `link-name`, `aria-*-name`, `aria-allowed-attr`, `aria-required-attr`, `aria-required-children`, `aria-required-parent`, `aria-roles`, `aria-valid-attr`, `aria-valid-attr-value`, `aria-hidden-focus`) — exactly the regression class the badge prop changes were meant to prevent (a future PR stripping `tooltip` / `aria-label` / `srLabel` and shipping a colour-only pill). The spec fails on critical/serious violations and surfaces moderate/minor ones as warnings; pages that render zero badges (when seeded data is empty, e.g. Dispatch with no jobs) emit a no-op warning instead of failing. Wired into `.github/workflows/admin-e2e.yml` alongside the other tenant smoke specs.
- **OpenAI Realtime voice drift detector:** A daily GitHub Action (`.github/workflows/check-openai-realtime-voices.yml`, 13:17 UTC + manual trigger) runs `scripts/check-openai-realtime-voices.ts`, which probes `POST https://api.openai.com/v1/realtime/sessions` with a deliberately invalid voice and parses the allowed-value list out of the resulting `error.message` (multiple wording patterns are supported). It diffs the discovered set against `VOICES` in `client-app/src/lib/agentVoices.ts` and on drift opens (or updates the body of) a single deduplicated tracking issue labeled `openai-voices-check`. When a subsequent run comes back in-sync, the workflow auto-closes any open tracking issue. Exit codes are split: 0=in-sync, 1=drift, 2=parser-broken, 3=request/auth failure. Requires the `OPENAI_API_KEY` secret. Unit tests live in `tests/scripts/checkOpenaiRealtimeVoices.test.ts`. Complements the existing review-cadence comment block and the CI guard from task #709.
- **i18n key sync gate:** `npm run check:i18n-keys` (via `scripts/check-i18n-keys.mjs`) walks every namespace shipped from `client-app/src/locales/{en,de,es,fr,pt-BR}/*.json` and asserts that every key in `en/<ns>.json` is present in every other locale file (and vice versa). The list of supported locales and namespaces is parsed out of `client-app/src/lib/i18n.ts`. Drift fails CI (exit 1) and prints the missing/extra dotted key paths. Intentional language-specific overrides are tolerated via `scripts/i18n-allowed-overrides.json`. The same logic is also covered by `tests/scripts/i18nKeyCheck.test.ts` so it runs under `vitest`. Wired into the existing PR `Typecheck` workflow and `scripts/post-merge.sh`. Catches the silent "user sees `vertical_agents_page.spotlight.partner_cta` instead of a translated string" regression.
- **Localized URL routing:** Visitors can land on `/<locale>/...` (e.g. `/pt-BR/pricing`, `/fr/docs`) or use `/?lang=<locale>` as a shareable, search-engine-indexable language signal. The URL prefix wins over `localStorage`/`navigator.language`, every page emits per-locale `<link rel="alternate" hreflang>` tags via the `SEO` component, and the language picker rewrites the URL on switch. Un-prefixed URLs continue to work; `/en/...` is accepted as an alias of `/...`. See `docs/i18n.md` for details.
- **Localized sitemap:** `client-app/public/sitemap.xml` is regenerated by `scripts/generate-sitemap.mjs` (invoked as `client-app`'s `prebuild` hook so every production build ships a fresh copy). It enumerates the public marketing routes from `client-app/src/App.tsx` plus the dynamic slug data files (`docs.ts`, `blogArticles.ts`, `guides.ts`, and the `verticals` map in `pages/public/VerticalLanding.tsx`) and emits one `<url>` per (path × supported locale) pair. Every entry — including the default-locale variant — carries the FULL set of `<xhtml:link rel="alternate" hreflang="…">` siblings (one per locale + `x-default` pointing at the un-prefixed English URL), which is the canonical signal Google/Bing use to pair localized variants without splitting link equity. Authenticated/in-app routes are intentionally excluded (they're already in `client-app/public/robots.txt` `Disallow`s); `robots.txt` advertises the sitemap via its `Sitemap:` directive. The locale list and `withLocalePrefix` rules are kept in sync with `client-app/src/lib/i18n.ts`. Regression-tested by `tests/scripts/generateSitemap.test.ts`.
- **Help Docs Localization:** The help-center articles defined in `client-app/src/data/docs.ts` are translated into all 5 supported locales via stable keys under `articles.<slug>.{title,description,body.<i>...}` and `categories.<slug>.{title,description}` in each `locales/<locale>/docs.json`. Translations are applied at render time by hooks in `client-app/src/lib/translateDoc.ts` (`useTranslatedArticle`, `useArticleMetaTranslator`, `useDocCategoryTranslator`) and the `translateBlocks` helper used by `DocBlocks`. New or updated articles are translated by re-running `npx tsx scripts/translate-docs.ts`, which extracts English source strings, calls OpenAI for missing/English-fallback values per locale, and writes results incrementally; re-runs are idempotent.
- **Frontend/Backend Communication:** Utilizes an API proxy and Server-Sent Events (SSE) for real-time data updates.
- **Federated Ingest API:** Allows external voice agent systems to push call completion and ticket creation events.
- **Native Agent Porting (Azul Vision):** Supports running Azul Vision's production agents within QVO's voice gateway.
- **Technician Mobile App (`mobile/`):** An Expo (React Native) app for field technicians, enabling job management, dispatch, appointment viewing, and customer communication.
