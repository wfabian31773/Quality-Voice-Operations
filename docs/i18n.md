# Internationalization (i18n)

The QVO client app (`client-app/`) is wired up with [i18next](https://www.i18next.com/) and
[react-i18next](https://react.i18next.com/) so the dashboard, marketing site, admin consoles, and
docs can be served in multiple languages.

## Currently supported locales

| Code    | Name                          |
| ------- | ----------------------------- |
| `en`    | English (default)             |
| `es`    | Español (Spanish)             |
| `pt-BR` | Português (Brazilian Portuguese) |
| `fr`    | Français (French)             |
| `de`    | Deutsch (German)              |

Each non-English locale covers:

- **Application shell**: public header/footer, tenant sidebar, admin sidebar, app footer, language
  switcher.
- **Marketing site (`marketing` namespace)**: every public page — Landing/home hero, Pricing,
  Features, Product, Use Cases, Demo, Contact, AI Agents (`AgentsShowcase`), Integrations, and
  industry vertical landing pages (`VerticalLanding`).
- **Docs**: alt text / captions for every screenshot in the seven integration walkthroughs
  (HubSpot, Google Calendar, Slack, Pipedrive, QuickBooks, Salesforce, Outlook).

All five locales (en, es, pt-BR, fr, de) ship with identical key sets in `marketing.json` so the
language picker on any marketing page flips visible copy without falling back to English.

Strings that have not been translated yet fall back to English automatically — there is no broken
"missing translation" UX while a new locale is being filled in.

### Deliberate scope: marketing data vs. chrome

Two marketing pages keep their per-record data hardcoded in English on purpose, and only their
"chrome" (page hero, section titles, CTA labels, channel/category labels, etc.) is translated:

- **`AgentsShowcase` (`/ai-agents`)**: the 12 prebuilt `AgentTemplate` records — agent names,
  descriptions, capabilities, example conversations, workflow steps, tools used, and escalation
  behavior — remain in English. Hero, category filters, channel badges, the "More detail" /
  "Deploy This Agent" controls, and the bottom CTA are translated under
  `marketing:agents_page.*`.
- **`VerticalLanding` (`/industries/:vertical`)**: the per-vertical `VerticalData` records (name,
  headline, subheadline, painPoints, agentExamples, stats, testimonial, metaTitle,
  metaDescription) remain in English. Section headers, the floating "Live performance" card,
  ROI/Why-QVO labels, and the bottom CTA are translated under `marketing:vertical_page.*`, with
  `{{vertical}}` / `{{vertical_lower}}` interpolations supplying the (English) industry name.

This split keeps the per-template marketing copy in one source of truth (English) while the
surrounding UI flips with the language picker. When/if the data records themselves need to be
localized, move them into `marketing.json` (or a sibling `agents.json` / `verticals.json`
namespace) and translate per-locale.

## Layout

```
client-app/
  src/
    lib/
      i18n.ts                     # i18next bootstrap, language detector, html-lang sync,
                                  # URL-prefix helpers (getLocaleFromPath, withLocalePrefix, …)
    components/
      LanguageSwitcher.tsx        # Visible switcher used in all app shells
      SEO.tsx                     # Per-page <title>/<meta>/canonical/hreflang manager
    locales/
      en/
        common.json               # App shell (nav, footer, actions, theme labels…)
        marketing.json            # Public marketing pages (landing, pricing, features, agents,
                                  # integrations, verticals, etc.)
        docs.json                 # Integration walkthrough alt + caption strings
        tenant.json               # Tenant portal strings
        admin.json                # Admin console strings
      es/  …                      # Same files as en/, identical key trees
      pt-BR/  …
      fr/  …
      de/  …
```

The provider is mounted in `client-app/src/main.tsx` (via `<I18nextProvider>` + `<Suspense>`).
`<html lang>` is updated dynamically whenever the language changes.

## URL-prefix locale routing

Every supported locale has a sticky URL form so links are shareable across language preferences
and search engines can index each language variant independently. The patterns:

| URL pattern                  | Resolved locale | Notes                                             |
| ---------------------------- | --------------- | ------------------------------------------------- |
| `/pricing`                   | `en` (default)  | Canonical English URL — un-prefixed.              |
| `/en/pricing`                | `en`            | Accepted alias of `/pricing`.                     |
| `/pt-BR/pricing`             | `pt-BR`         | Canonical Portuguese URL.                         |
| `/fr/docs/getting-started`   | `fr`            | Locale prefix wins regardless of browser/locale.  |
| `/?lang=pt-BR`               | `pt-BR`         | Query-string fallback for campaign / share links. |

Whichever variant a visitor lands on is the language they see — `/pt-BR/...` always renders
Portuguese even if the recipient's browser is configured for English, and vice versa. That's
what makes a "marketing page in my language" link forwardable.

### How it's wired

- `getLocaleFromPath(pathname)` in `client-app/src/lib/i18n.ts` returns the supported locale code
  when the first path segment matches one of `SUPPORTED_LANGUAGES` (case-insensitive — `/pt-br`
  resolves the same as `/pt-BR`). Returns `null` for un-prefixed or unsupported segments.
- `client-app/src/main.tsx` calls `getLocaleFromPath(window.location.pathname)` once at boot and
  passes the result to `<BrowserRouter basename={…}>`. From that point on every `<Link to="/foo">`
  inside React Router is automatically prefixed with the active locale, so a click on
  `/pt-BR/pricing → /features` keeps the user on `/pt-BR/features`.
- A custom i18next detector (`urlPath`) reads the same path prefix at init time so i18next's
  resolved language matches the basename. The detector chain is now
  `['urlPath', 'querystring', 'localStorage', 'navigator', 'htmlTag']` — the URL is the
  authoritative signal, with `?lang=…` (key: `lang`) accepted as a query-string alternate.
- `LanguageSwitcher` builds the new URL with `withLocalePrefix(nextLocale, currentPath)` and
  performs a full-page `window.location.assign(...)`. The full reload is intentional: the router
  basename is fixed at boot, so swapping the prefix requires a fresh mount. The previous
  selection is also written to `localStorage["qvo_lang"]` so subsequent visits to un-prefixed
  pages still honor the choice.
- `SEO` emits one `<link rel="alternate" hreflang="…">` tag per supported locale on every page,
  plus an `x-default` pointing at the un-prefixed English URL. Each tag points at the correct
  per-locale URL of the current page (e.g. on `/features` we emit `<link rel="alternate"
  hreflang="pt-BR" href="https://…/pt-BR/features">`). `client-app/index.html` ships a static
  baseline of hreflang tags for the home page so JS-disabled crawlers see them too.

### Backwards compatibility

- All existing un-prefixed URLs (`/pricing`, `/docs`, `/dashboard`, …) continue to work
  unchanged — there is no redirect.
- `/en/...` is accepted as an alias of `/...` for symmetry.
- Visitors with an existing `localStorage["qvo_lang"]` who land on an un-prefixed URL still see
  their previously chosen language — only landing on a prefixed URL overrides it for that visit.

### Helpers

```ts
import {
  getLocaleFromPath,    // /pt-BR/pricing → 'pt-BR' | null
  stripLocalePrefix,    // /pt-BR/pricing → /pricing
  withLocalePrefix,     // ('pt-BR', '/pricing') → '/pt-BR/pricing'
  resolveSupportedLanguage,
  SUPPORTED_LANGUAGES,
  DEFAULT_LANGUAGE,
} from './lib/i18n';
```

`withLocalePrefix` is idempotent — passing in an already-prefixed path strips the existing
prefix before applying the new one, so it's safe to call on the current `location.pathname`
without manual normalization.

## How language is selected

The detection order on first load is:

1. **URL path prefix** (e.g. `/pt-BR/...`) — wins over everything; the URL is authoritative.
2. **`?lang=` query string** — useful for campaign / share links (`/pricing?lang=pt-BR`).
3. **`localStorage["qvo_lang"]`** — set by the visible Language picker; persists between visits.
4. **`navigator.language`** — the browser's preferred language.
5. **`<html lang>`** attribute — defaults to `en`.

Once a visitor picks a language manually via the picker, the choice is written to
`localStorage["qvo_lang"]` *and* the URL is rewritten to include the prefix (`/pricing` →
`/pt-BR/pricing`). On future visits to un-prefixed URLs, localStorage takes over and surfaces
the saved choice.

### Matching `navigator.language` to a supported locale

The browser's `navigator.language` is rarely an exact match for one of our supported codes — it is
usually a regional variant like `pt-PT`, `fr-CA`, `de-AT`, or `en-US`. To make sure first-time
visitors land in the right language, every value the detector returns is run through
`resolveSupportedLanguage` (configured as i18next's `detection.convertDetectedLanguage`) before
i18next sees it. The mapping rules are:

1. Exact match wins (e.g. `pt-BR` → `pt-BR`).
2. Any Portuguese variant maps to `pt-BR`, since that is the only Portuguese locale we ship today
   (`pt`, `pt-PT`, `pt-AO`, … → `pt-BR`).
3. Otherwise, match by primary subtag — `fr-CA` and `fr-FR` → `fr`, `de-AT` and `de-CH` → `de`,
   `es-MX` and `es-AR` → `es`, `en-US` and `en-GB` → `en`.
4. If nothing matches (e.g. `ja`, `zh`), we fall back to English.

> Implementation note: we deliberately do **not** enable i18next's `nonExplicitSupportedLngs`
> option. A previous attempt to use it broke resource resolution for `pt-BR` because i18next would
> strip the region and try to load a non-existent `pt` bundle. Doing the mapping ourselves keeps
> i18next's resolved language as one of our exact supported codes.

## Using translations in components

```tsx
import { useTranslation } from 'react-i18next';

export default function Example() {
  const { t } = useTranslation();
  return <button>{t('actions.sign_in')}</button>;
}
```

For values that live in a non-default namespace (e.g. the `docs` namespace) call:

```tsx
const { t } = useTranslation('docs');
t('images.salesforce-app-manager.alt');
```

Use placeholders for variable interpolation:

```tsx
t('footer.rights', { year: new Date().getFullYear() });
```

## Translating screenshot alt + caption text in `client-app/src/data/docs.ts`

Image blocks for the seven integration walkthroughs are auto-translated by `DocBlocks.tsx`. The
translator derives a stable `imageId` from the image filename (e.g.
`/docs/screenshots/hubspot-create-app.svg` → `hubspot-create-app`) and looks up
`docs:images.<imageId>.alt` and `docs:images.<imageId>.caption`.

To localize a new screenshot:

1. Keep the English literal as the `alt` and `caption` on the `DocBlock` in `docs.ts` — that is
   what English speakers see and the fallback for any locale that hasn't translated it yet.
2. Add a key under `images.<imageId>` in `client-app/src/locales/<lang>/docs.json` for every
   locale you support, where `<imageId>` is the filename (without extension) of the screenshot.

If a key is missing for the active locale, the English literal in `docs.ts` is shown — there is no
"key not found" failure.

## Adding a new locale

1. Pick a [BCP-47 code](https://www.iana.org/assignments/language-subtag-registry/language-subtag-registry)
   (e.g. `fr` for French, `pt-BR` for Brazilian Portuguese).
2. Create `client-app/src/locales/<code>/{common,marketing,docs,tenant,admin}.json` by copying
   the English files and translating each value. Keep the keys identical — only the right-hand
   strings change. (`marketing.json` covers every public marketing page; missing keys silently
   fall back to English.)
3. Register the language in `client-app/src/lib/i18n.ts`:

   - Add it to `SUPPORTED_LANGUAGES` (`code`, `label`, `nativeLabel`).
   - Import the new JSON files and add them to the `resources` map.

   That's it — the picker in every shell will list the new option automatically, and
   `/<code>/...` URLs will start resolving to the new locale.

4. Add a static `<link rel="alternate" hreflang="<code>" href="/<code>" />` tag to
   `client-app/index.html` so the home-page baseline announces the new locale to JS-disabled
   crawlers. (The `<SEO>` component picks up new languages automatically from
   `SUPPORTED_LANGUAGES` for every other page.)

5. Smoke-test by switching to the new locale in the picker and clicking through the public site,
   the tenant portal, the admin console, and at least one integration walkthrough doc page.

## Adding new translatable strings

1. Replace the literal in the React component with `t('namespace.path.to.key')`.
2. Add the key to **every** locale file under `client-app/src/locales/<lang>/<namespace>.json`.
   English entries should always be authored first because the rest of the app falls back to them.
3. Group new keys under the existing top-level sections (e.g. `tenant_nav.*`, `footer.*`) so the
   files stay browseable.

## Keeping locales in sync

There is no automated extractor yet. To audit drift between English and another locale, diff the
key trees:

```bash
node -e "const a=require('./client-app/src/locales/en/common.json'),b=require('./client-app/src/locales/es/common.json');\
const flat=(o,p='')=>Object.entries(o).flatMap(([k,v])=>typeof v==='object'?flat(v,p+k+'.'):[p+k]);\
const A=new Set(flat(a)),B=new Set(flat(b));\
console.log('Missing in es:', [...A].filter(k=>!B.has(k)));\
console.log('Extra in es:',  [...B].filter(k=>!A.has(k)));"
```

Repeat for `marketing.json`, `docs.json`, `tenant.json`, `admin.json` and any future namespaces.
A missing key is non-fatal at runtime (English falls back), but the audit is the recommended way
to catch drift before shipping a release.

For `marketing.json` specifically, all five locales must agree on every key — the parity check
should report `missing: 0, extra: 0` for every non-English locale before a release.
