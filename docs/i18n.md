# Internationalization (i18n)

The QVO client app (`client-app/`) is wired up with [i18next](https://www.i18next.com/) and
[react-i18next](https://react.i18next.com/) so the dashboard, marketing site, admin consoles, and
docs can be served in multiple languages.

## Currently supported locales

| Code    | Name                          |
| ------- | ----------------------------- |
| `en`    | English (default)             |
| `es`    | Español (Spanish)             |
| `pt-BR` | Português (Brazilian Portuguese) |
| `fr`    | Français (French)             |
| `de`    | Deutsch (German)              |

Each non-English locale covers the application shell (public header/footer, tenant sidebar, admin
sidebar, app footer, language switcher) and the alt text / captions for every screenshot in the
seven integration walkthroughs (HubSpot, Google Calendar, Slack, Pipedrive, QuickBooks, Salesforce,
Outlook).

Strings that have not been translated yet fall back to English automatically — there is no broken
"missing translation" UX while a new locale is being filled in.

## Layout

```
client-app/
  src/
    lib/
      i18n.ts                     # i18next bootstrap, language detector, html-lang sync
    components/
      LanguageSwitcher.tsx        # Visible switcher used in all app shells
    locales/
      en/
        common.json               # App shell (nav, footer, actions, theme labels…)
        docs.json                 # Integration walkthrough alt + caption strings
      es/
        common.json
        docs.json
      pt-BR/
        common.json
        docs.json
      fr/
        common.json
        docs.json
      de/
        common.json
        docs.json
```

The provider is mounted in `client-app/src/main.tsx` (via `<I18nextProvider>` + `<Suspense>`).
`<html lang>` is updated dynamically whenever the language changes.

## How language is selected

`i18next-browser-languagedetector` resolves the active language using this order:

1. `localStorage["qvo_lang"]` — set by the visible Language picker in every shell
2. The browser's `navigator.language`
3. The `<html lang>` attribute (defaults to `en`)
4. The `fallbackLng` (`en`)

Because the choice is persisted to `localStorage`, it survives page reloads and is shared between
the marketing site, the tenant portal, the admin console, and the docs viewer for the same
browser/profile.

### Matching `navigator.language` to a supported locale

The browser's `navigator.language` is rarely an exact match for one of our supported codes — it is
usually a regional variant like `pt-PT`, `fr-CA`, `de-AT`, or `en-US`. To make sure first-time
visitors land in the right language, every value the detector returns is run through
`resolveSupportedLanguage` (configured as i18next's `detection.convertDetectedLanguage`) before
i18next sees it. The mapping rules are:

1. Exact match wins (e.g. `pt-BR` → `pt-BR`).
2. Any Portuguese variant maps to `pt-BR`, since that is the only Portuguese locale we ship today
   (`pt`, `pt-PT`, `pt-AO`, … → `pt-BR`).
3. Otherwise, match by primary subtag — `fr-CA` and `fr-FR` → `fr`, `de-AT` and `de-CH` → `de`,
   `es-MX` and `es-AR` → `es`, `en-US` and `en-GB` → `en`.
4. If nothing matches (e.g. `ja`, `zh`), we fall back to English.

Once a visitor picks a language manually, that choice is written to `localStorage["qvo_lang"]` and
takes priority over `navigator.language` on every subsequent visit — auto-detection only kicks in
when no manual choice has been made yet.

> Implementation note: we deliberately do **not** enable i18next's `nonExplicitSupportedLngs`
> option. A previous attempt to use it broke resource resolution for `pt-BR` because i18next would
> strip the region and try to load a non-existent `pt` bundle. Doing the mapping ourselves keeps
> i18next's resolved language as one of our exact supported codes.

## Using translations in components

```tsx
import { useTranslation } from 'react-i18next';

export default function Example() {
  const { t } = useTranslation();
  return <button>{t('actions.sign_in')}</button>;
}
```

For values that live in a non-default namespace (e.g. the `docs` namespace) call:

```tsx
const { t } = useTranslation('docs');
t('images.salesforce-app-manager.alt');
```

Use placeholders for variable interpolation:

```tsx
t('footer.rights', { year: new Date().getFullYear() });
```

## Translating screenshot alt + caption text in `client-app/src/data/docs.ts`

Image blocks for the seven integration walkthroughs are auto-translated by `DocBlocks.tsx`. The
translator derives a stable `imageId` from the image filename (e.g.
`/docs/screenshots/hubspot-create-app.svg` → `hubspot-create-app`) and looks up
`docs:images.<imageId>.alt` and `docs:images.<imageId>.caption`.

To localize a new screenshot:

1. Keep the English literal as the `alt` and `caption` on the `DocBlock` in `docs.ts` — that is
   what English speakers see and the fallback for any locale that hasn't translated it yet.
2. Add a key under `images.<imageId>` in `client-app/src/locales/<lang>/docs.json` for every
   locale you support, where `<imageId>` is the filename (without extension) of the screenshot.

If a key is missing for the active locale, the English literal in `docs.ts` is shown — there is no
"key not found" failure.

## Adding a new locale

1. Pick a [BCP-47 code](https://www.iana.org/assignments/language-subtag-registry/language-subtag-registry)
   (e.g. `fr` for French, `pt-BR` for Brazilian Portuguese).
2. Create `client-app/src/locales/<code>/common.json` and `client-app/src/locales/<code>/docs.json`
   by copying the English files and translating each value. Keep the keys identical — only the
   right-hand strings change.
3. Register the language in `client-app/src/lib/i18n.ts`:

   - Add it to `SUPPORTED_LANGUAGES` (`code`, `label`, `nativeLabel`).
   - Import the new JSON files and add them to the `resources` map.

   That's it — the picker in every shell will list the new option automatically.

4. Smoke-test by switching to the new locale in the picker and clicking through the public site,
   the tenant portal, the admin console, and at least one integration walkthrough doc page.

## Adding new translatable strings

1. Replace the literal in the React component with `t('namespace.path.to.key')`.
2. Add the key to **every** locale file under `client-app/src/locales/<lang>/<namespace>.json`.
   English entries should always be authored first because the rest of the app falls back to them.
3. Group new keys under the existing top-level sections (e.g. `tenant_nav.*`, `footer.*`) so the
   files stay browseable.

## Keeping locales in sync

There is no automated extractor yet. To audit drift between English and another locale, diff the
key trees:

```bash
node -e "const a=require('./client-app/src/locales/en/common.json'),b=require('./client-app/src/locales/es/common.json');\
const flat=(o,p='')=>Object.entries(o).flatMap(([k,v])=>typeof v==='object'?flat(v,p+k+'.'):[p+k]);\
const A=new Set(flat(a)),B=new Set(flat(b));\
console.log('Missing in es:', [...A].filter(k=>!B.has(k)));\
console.log('Extra in es:',  [...B].filter(k=>!A.has(k)));"
```

Repeat for `docs.json` and any future namespaces. A missing key is non-fatal at runtime (English
falls back), but the audit is the recommended way to catch drift before shipping a release.
