# SMS inbox robustness

Owner/staff two-way SMS inbox (`server/admin-api/routes/smsInbox.ts`). The voice agent does not call these routes; it uses `sms.send` / `sms.send_confirmation.*` (tools-spec §2.4). This doc is for the HTTP adapter the owner UI uses.

## Guaranteed now

- **Write validation.** PUT/PATCH thread, POST messages, POST notes, POST bulk-update, template create/update/substitute, auto-reply create/update, and assignment-rule create reject bad bodies with `400 { error, fields }` before any database write. Extra keys are rejected (`.strict()`). Bulk-update accepts at most 200 ids.
- **Reply idempotency.** `POST /sms-inbox/threads/:id/messages` reads an optional `Idempotency-Key` header and namespaces it (`sms:inbox:{tenantId}:{threadId}:{key}`). Immediate replies pass it to `sendUserSms`: the `sms.send` chokepoint returns the stored result for the same key + same body without sending a second text. Scheduled replies use `action_idempotency` under `sms.inbox.schedule`, with the same 24-hour expiry as `sms.send` and a SHA-256 hash of canonical `{ threadId, body, scheduledAt }` (time normalized to ISO). The claim, scheduled message row, conversation preview, and completed result commit in one tenant transaction; concurrent duplicates wait and replay the original message by its stored id with a tenant-scoped lookup. A changed body or time returns `409` with `code: 'IDEMPOTENCY_KEY_REUSED'`. Only a new scheduled row logs `message_scheduled`. The composer sends one key per draft and reuses it on retries; callers without a key still create a new scheduled row per request (or get a fresh `sms:user:{uuid}` for an immediate reply).
- **Final vs ambiguous send failures.** A non-retryable provider rejection (Twilio auth/permission/invalid-number-style `UPSTREAM_UNAVAILABLE`, plus opt-out / not-enabled / invalid number) is returned with `final: true`. Twilio auth/permission rejections that used to look like HTTP 500 `UPSTREAM_UNAVAILABLE` are `422 { reason: 'provider_rejected', code: 'PROVIDER_REJECTED', final: true }`. The route then deletes the `sms.send` idempotency row (`releaseSmsInboxReplyIdempotency`) so a later attempt can run, but only if that row is still a completed final-rejection failure (`ok: false`, `retryable: false`, and not a key-conflict / pre-claim error). A success written for the same key in between is left intact. It does **not** delete on `IDEMPOTENCY_KEY_REUSED` (or pre-claim `VALIDATION_FAILED` / `FORBIDDEN`): that row belongs to a previous payload, often a success, and dropping it would let a retry of the original body double-send. An initial retryable failure stays HTTP 500 without `final`, and the action runtime releases its key. The composer keeps the key after unmarked 5xx, 429, quiet-hours/DNC 403s, and network errors; the protected unknown-outcome replay below returns a 409 warning.
- **Ambiguous transmit replay.** Immediate sends commit `metadata.transmitOutcome = 'unknown'` with `transmitAttemptId` before calling Twilio. A plain transport error/timeout leaves the row `sending`; the existing `?mid=` StatusCallback can attach its SID and move it to queued/sent/delivered. A definite `TwilioApiError` HTTP rejection (including retryable 503/429) or a marker-write failure records `not_sent` and keeps the existing retry behavior. Before reserving another row, a keyed `sms.send` checks outbound rows for the same tenant, normalized recipient, and metadata key created within the 24-hour idempotency window. A marker plus unknown outcome replays the original `messageId` as `ok: true, status: 'sending', reason: 'SEND_OUTCOME_UNKNOWN'`; a saved SID replays success as `queued` with the original id/SID. Using an OK replay avoids changing the shared action error union and lets the runtime cache the protected result. The inbox adapts the unknown replay to `409 { error: 'This message may already have been sent. Check the thread before sending again.', code: 'SEND_OUTCOME_UNKNOWN', reason: 'send_outcome_unknown', messageId }`, without releasing the action key or logging a new send. The existing composer shows that warning, keeps the draft, and rotates its key on 409 so a deliberate resend is possible after checking the thread. An unknown replay already cached by the runtime continues to warn even if a callback later attaches a SID; the thread is the source of delivery status. No key means no row-lookup deduplication. No migration or index is needed; the lookup filters tenant/direction/recipient/time before metadata. The deferred-release path is unchanged.
- **Single send chokepoint.** Immediate inbox replies call `sendUserSms`; the scheduled dispatcher calls `sendStoredSms`. Both are `sms.send`. An opted-out recipient is `403` with `{ error, reason: 'recipient_opted_out', code: 'RECIPIENT_OPTED_OUT' }` (the chokepoint's message); Twilio is not called.
- **Tenant isolation.** Every write looks up the thread/template/rule with `tenant_id` from the session. A tenant-B id is `404` and the mutation is not invoked. Bulk-update walks the id list, keeps only rows `getConversation` returns for this tenant, and updates those; foreign ids are skipped (`updated` counts only own rows).
- **Activity log.** Assignment, close, reopen, bulk-update (per own thread), and notes each write a `logActivity` row (`assigned`, `status_changed`, `tagged`, or `note_added` — the existing check constraint). Close/reopen on a single thread already logged `status_changed`; bulk-update previously only wrote the platform audit log.

- **Composer retry keys.** The composer sends an `Idempotency-Key` on every reply (one key per draft: reused when the same text/schedule is retried on the same thread, rotated after success, any edit, or a `final: true` / 400 / 404 / 409 / opt-out / not-enabled rejection; other 403s and 429 keep the key because the route can return them before the idempotency lookup) and ignores a second submit while one is in flight (`client-app/src/pages/SmsInbox.tsx`, tests in `SmsInbox.test.tsx`).

## Still open

- `releaseSmsInboxReplyIdempotency` is best-effort: if the DELETE fails, the client still rotates on `final: true`, but another client that reused the same key would keep seeing the cached failure until the row expires. The DELETE itself only matches a row that is still that final-rejection failure, so a delayed cleanup cannot drop a later success.
- Replaying a reply with a key writes a second `message_sent` activity row (the SMS is not resent). Skip activity on chokepoint replay if that becomes noisy.
- Notes / template / rule writes are not keyed for HTTP idempotency.
- `PUT /sms-inbox/compliance-settings` and `POST /sms-inbox/ai-draft` are outside this validation pass.
- Quiet-hours deferrals are logged as `message_scheduled` with `details.reason = 'sms_quiet_hours'` and `details.deferred = true`; readers accept both `message_scheduled` and legacy `message_deferred` rows with that reason.
- Extracting inbox writes into `sms.reply` / `sms.assign` / `sms.close` / `sms.add_note` actions (tools-spec §2.4) is still the larger adapter split.
